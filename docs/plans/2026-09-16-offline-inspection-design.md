# 离线验货 App 设计

## 目标

基于 uni-app X 构建 Android 与 iOS 验货 App。首期完成登录、会话恢复、验货列表、查询计划、下载计划、本地 SQLite 持久化和通用离线同步入口，并尽量保持旧 H5 的接口参数、返回数据及本地报告结构一致。

## 总体架构

页面不直接调用 `uni.request` 或 SQLite。调用链分为两条：

1. `页面/组件 -> Service -> ApiRequestQueue -> ApiClient -> 后端`
2. `页面/组件 -> Service -> Repository -> Database -> SQLite`

所有 HTTP 请求先进入运行时请求队列。登录和查询属于即时任务；下载、提交、上传和状态同步属于可持久化任务，断网或请求失败时写入 `request_queue`，网络恢复后由同步服务继续执行。

## 目录职责

- `api/`：后端接口定义，不包含页面状态。
- `core/queue/`：请求排队、优先级、去重和重试策略。
- `database/`：SQLite 契约、表结构、迁移与平台适配。
- `repositories/`：用户、计划和请求队列的数据访问。
- `services/`：登录、列表、下载和离线同步业务流程。
- `components/inspection/`：可复用验货列表项。
- `components/sync/`：多页面可使用的同步状态组件。
- `composables/`：页面复用的同步状态与生命周期逻辑。

## 数据模型

保留旧 H5 的核心表和字段：

- `user`：本地会话、Token、角色及登录偏好。
- `report`：本地验货计划摘要和完整 `jsonData`。
- `checklist`：验货检查项。
- `defect`：缺陷记录。
- `photo`：本地媒体及上传状态。
- `sync_log`：同步错误和重试日志。

新增：

- `request_queue`：可恢复接口任务，包含任务类型、请求参数、状态、重试次数、去重键和下次执行时间。
- `schema_migration`：数据库版本与迁移记录。

计划状态继续使用旧 H5 约定：`0` 为已定计划，`1/2` 归入进行中，`3` 为已完成。

## 登录流程

App 启动后先初始化数据库，再读取最近一次本地会话。有有效会话则进入列表，否则进入登录页。在线登录调用 `/api/auth/login`，成功后将标准化用户数据保存到 `user` 表。离线时仅允许使用曾经成功登录并仍保留本地会话的身份进入，不保存明文密码。

## 列表与查询流程

列表启动时先从 SQLite 读取本地摘要并立即展示，再在联网时查询远端数据。本地与远端数据使用 `planId/reportId` 合并，本地记录优先，避免远端数据覆盖未同步修改。

列表项使用独立的 `InspectionPlanCard.uvue`，负责订单号、供应商、产品、货号、验货类型、状态、进度、下载、锁定及合并标识展示，并通过事件向页面报告点击和操作。

列表底部提供固定的“查询验货”按钮，进入查询页。下载完成后，在单个 SQLite 事务中标准化并保存返回数据，随后返回列表；列表通过 `onShow` 重新读取本地数据，因此下载项立即进入已定计划列表。

## 离线同步

`offlineSyncService.uts` 是唯一同步执行入口，负责网络判断、队列扫描、任务锁定、执行、重试和失败日志。`OfflineSyncStatus.uvue` 只负责展示状态与触发同步，`useOfflineSync.uts` 负责页面订阅和网络恢复事件，因此同一同步入口可以用于列表、详情和设置页面。

同步规则沿用旧 H5：完成报告不得再次生成；合并验货子计划不独立提交；缺少同步载荷的脏数据记录失败；单条失败不阻断后续任务；任务达到最大重试次数后进入失败状态并保留错误信息。

## 首期边界

首期实现登录、退出、会话恢复、三状态列表、查询、分页、下载、本地列表、队列状态和手动/自动同步入口。合并、拆分、扫码、详情编辑、缺陷、拍照和提交报告保留数据字段与组件事件，在后续阶段逐项实现。

## 验证策略

纯 UTS 业务模块保持为 TypeScript 兼容语法，由 Node 测试直接加载源文件，覆盖状态归一化、列表合并、队列顺序、去重、重试和下载结果拆分。原生 SQLite 插件需分别在 Android 与 iOS 真机验证建库、事务、参数绑定、迁移和重启持久化。
