# App 图片排序对齐设计

## 目标

补齐 H5 检查项图片排序能力。用户在检查项编辑弹层中调整图片顺序后，App 立即更新本地展示顺序和每张图片的 `sortNo`，并通过现有普通报告草稿持久化与同步链路保存；最终提交规则保持不变。

## 方案选择

1. 直接移植 H5 的 DOM 拖拽：视觉最接近，但依赖元素矩形、`document` 监听和浏览器拖拽细节，不符合 App 禁止浏览器 API 的约束。
2. 原生坐标拖拽：可以接近 H5，但需要平台布局测量和复杂触摸状态，首版风险较高。
3. 点击式换位：先选择图片，再点击目标位置完成移动。结果与 H5 相同，不依赖 DOM，Android/iOS 行为稳定。

采用方案 3。弹层仍使用 H5 的三列图片网格、序号和完成操作，只调整原生端交互提示。

## 数据流

- `domain/mediaSort.uts` 提供不可变换位和连续 `sortNo` 归一化纯函数。
- `PhotoSortSheet.uvue` 复制传入图片，用户完成换位后发出业务事件 `sorted`。
- `CheckItemSheet.uvue` 在图片数量大于一张时展示“调整顺序”，接收排序结果并发出 `photos-sorted`。
- `pages/report/detail.uvue` 使用现有 `updateChecklistItem` 更新普通或合并检查项数据，并调用现有延迟草稿保存。
- 排序不进入最终提交队列，也不触发 `finishFlag=1`；联网时由普通草稿同步，离线时保留在本地持久化队列。

## 错误与边界

- 少于两张图片时不展示排序入口。
- 非法起止索引返回连续编号的原顺序，不丢失图片对象和上传状态。
- 每次换位后都重新生成从 1 开始的 `sortNo`。
- 关闭弹层不保存临时排序；点击完成后才更新检查项草稿。

## 验证

- 纯函数测试覆盖向前移动、向后移动、非法索引和不可变性。
- UI 契约测试覆盖独立底部弹层、语义事件、详情页持久化接线。
- 运行 `npm test`，并扫描新增实现不使用 DOM、SVG、Blob URL 或浏览器存储。
